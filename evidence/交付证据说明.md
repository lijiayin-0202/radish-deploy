## 2. meegle 工作项编号校验流程

规范要求（`commit-convention.md` 第 55~61 行、`AGENTS.md` 2.4）：**`feat`、`fix` 类型提交前**必须由 AI 执行并保留实际输出：

```bash
meegle workitem get --work-item-id <数字编号> --project-key r17te9
```

| 步骤 | 要求 |
| --- | --- |
| 1 | 学生给出飞书项目真实工作项 ID（需求或缺陷），编号须与本次变更对应；不得只验证「数字存在」或关联无关工作项 |
| 2 | 保存命令、执行时间、完整结果、退出码；普通缺陷须先登记 Bug，`fix` 才能引用 |
| 3 | 校验失败 / 编号不存在 / 查询失败 → **禁止提交**，提醒学生确认（C-05）；不得默认改用其他 project-key |
| 4 | 不得伪造编号、不得声称查询成功；核验输出随作业提交 |

**本轮真实状态**：`Get-Command meegle` 无结果，本机未安装该 CLI；也没有经核验的真实工作项 ID。因此用户指定的首次提交 `feat: 电商订单售前退款完整业务实现` **未完成编号核验**，且格式与规范不符，属「初始化基线提交」，不得视为合规 `feat` 提交（偏差明细见 `docs/git-提交指引.md` 第 2.1 节）。

## 3. CI/CD 流程说明（当前未配置、未运行）

仓库当前无 `.yml` / `.yaml` 流水线文件，无远端，故**不存在任何真实 CI/CD 运行记录**。后续流水线应至少包含：

| 阶段 | 应执行命令 / 动作 | 应保留证据 |
| --- | --- | --- |
| 检出 | 检出 `dev/01` 或 `main` 的实际提交，记录 `git rev-parse HEAD` | 提交哈希与版本对应关系 |
| 依赖与格式 | `go mod download`、`gofmt -l .` | 原始输出 |

| 竞态检测 | `CGO_ENABLED=1 go test ./... -race -count=1`（环境须具备 C 编译器与真实 MySQL(InnoDB) 测试库） | race 原始输出，无数据竞争报告 |

| 部署与冒烟 | 部署对应发布提交，访问 `/health` 与五组场景关键路径 | 部署地址、冒烟结果、回滚说明 |

## 4. GitHub MCP 建仓流程说明

`AGENTS.md` 2.1 要求：通过 **GitHub MCP** 创建本题独立仓库，保留工具名称、请求与结果、时间、仓库 URL；**不得用手工或 CLI 创建记录替代 MCP 证据**。后续应：

1. 由学生在具备 MCP 的环境调用建仓工具，保存工具名、请求参数、响应、时间与仓库 URL。
2. 默认主分支 `main`；配置禁止直接推送、禁止删除、禁止强推，仅允许状态检查通过的 PR 合并。
3. 创建 `dev/01` 并关联远端，推送本地提交链（`git remote add origin <仓库 URL>` → `git push -u origin dev/01`）。
4. 全部业务、测试、原型、约束、Skill、配置与文档变更仍在 `dev/01` 提交。

**本轮真实状态**：`git remote -v` 为空，无 MCP 建仓记录，没有远程仓库，也没有 PR / 合并记录。本地 Git 提交链完整（有首次提交与有效 HEAD），后续推送远端即可继续全链路；但**不得把本地提交写成已完成 PR / 已上线**。
