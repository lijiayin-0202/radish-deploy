# 完成声明边界（开发草稿 vs 门禁验收通过）

> 本文件用于消除「AI 说已完成」与「客观门禁已通过」之间的歧义，供三个 Agent 与学生共同遵守。

## 1. 两类声明的定义

| 类型 | 含义 | 允许使用的措辞 | 禁止使用的措辞 |
| --- | --- | --- | --- |
| **开发草稿完成声明** | 代码、接口、文档、用例草案已写出并通过开发会话自检（编译、静态检查、单元测试、本地 HTTP 演示）。不代表已通过三轮验证、不代表可发布 | 「开发产物已就绪」「草案已生成」「可提交测试 Agent 验证」「本地自检通过」 | 「验收通过」「门禁通过」「测试全部通过」「可上线」「已部署」「可合并」 |
| **门禁验收通过声明** | 第 1 轮（单元测试 + 覆盖率 ≥85% + `go test -race` 无数据竞争）、第 2 轮（Apipost 用例真实运行导出）、第 3 轮（浏览器页面验收）全部有原始输出与版本对应，且 PR 状态检查通过 | 「第 N 轮门禁通过」「验收通过，可发起 PR」「可合并/可发布」 | 在无原始输出、无退出码、无运行导出时使用上述措辞 |

## 2. 判定门槛（不可跳过、不可倒序）

| 轮次 | 必须成立的客观事实 | 证据 |
| --- | --- | --- |
| 第 1 轮 | `gofmt -l` 无输出、`go vet` exit=0、`go test ./...` 通过、整体与核心业务包覆盖率 ≥85%、`go test -race` 在 `CGO_ENABLED=1` 环境通过且无数据竞争报告 | 命令原始输出、退出码、`coverage.out`、`coverage-all.out`、`race-output-raw.txt` |
| 第 2 轮 | 接口清单定稿、`api/v1` 实现完成、Apipost 48 用例真实运行并导出通过/失败结果 | `apipost-run-export.json`、运行标识、断言结果 |
| 第 3 轮 | `V-01~V-08` 可操作页面可用，验收 Agent 独立会话逐项结论 | 验收会话导出、验收报告、页面截图/录屏（脱敏） |
| 发布 | 全部提交在 `dev/01`、编号核验真实、PR 状态检查通过、主分支发布版本重新门禁、部署地址与冒烟结果 | PR/合并记录、CI 运行、部署与冒烟记录 |

## 4. 学生核验清单（确认阶段完成前逐项打勾）

1. 打开 `race-output.txt` 与 `scripts/run-race.ps1`，确认当前环境是否真的能跑 race；不能跑则不得声明第 1 轮通过。
2. 打开 `coverage-report.md`，区分「本机草案数值」与「真实 MySQL(InnoDB) 环境正式数值」。
3. 打开 `apipost-run-summary.md`，确认是否存在 Apipost 运行标识与导出文件。
4. 打开 `evidence/交付证据说明.md`，确认 meegle 核验、PR、CI、部署、视频与群提交记录是否齐全。
5. 任一项缺失时，只能声明「开发草稿完成／可提交测试 Agent 验证」，不得声明「验收通过」。
