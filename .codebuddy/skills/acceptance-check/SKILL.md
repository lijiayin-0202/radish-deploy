# 验收检查技能（acceptance-check）

## Overview

为 `shop-trade` 题目 01 提供「依据原始题面核对最终交付版本」的验收检查 Skill。它只做**只读核查与逐项结论**，不产出业务代码、不替学生修复缺陷、不把环境缺失误判为代码缺陷。补齐 `.agent/06` `K-02` 要求的验收检查 Skill 缺口。

## 用途

- 依据原始题面、三份上游文档与 `AC-01~AC-25`，逐项核对业务正确性、权限、数据一致性、错误处理、可维护性与敏感信息处理。
- 核对五组强制场景 `TST-S1~S5`、异常边界、原型显隐矩阵与 `M-01~M-30` 文案。
- 核对三轮验证证据、PR 门禁、版本对应关系，并把未通过项分类为「代码/产物缺陷」「环境/权限缺失」「过程证据缺失」。
- 输出逐项「通过 / 不通过」结论与证据位置，供验收 Agent 在独立会话中使用。

## 触发场景

- 用户要求「验收」「核对题面」「逐项检查交付清单」「PR 前门禁核验」「ACC-01~05」。
- 用户要求区分代码缺陷与环境限制、复核整改产物是否破坏既有接口。
- 拿到一份检查报告或评分结果，需要逐条验证整改是否落地。

### 不触发

- 生成 `model.go` / `schema.sql` / service 业务代码 / 单元测试 / Apipost 用例 / 页面 / 部署脚本。
- 修改生产代码、测试代码、验收报告结论之外的既有文件，或替开发 / 测试 Agent 修复缺陷。
- 执行或伪造 `go test -race`、真实 MySQL、meegle 核验、CI/CD、部署与视频证据。
- 在无原始输出时给出「验收通过 / 可合并 / 已上线」结论。

## 上层约束（强制）

| 维度 | 固定口径 |
| --- | --- |
| 项目 | `shop-trade`，仅题目 01；不得混入题目 02～20 业务场景 |
| 优先级 | 原始题面 ＞ 需求文档 ＞ 原型设计文档 ＞ 任务规划文档 ＞ 假设清单 ＞ `AGENTS.md` / `.agent/` 约束 ＞ 本 Skill |
| 技术栈 | GVA 单体 + Gin + GORM + MySQL(InnoDB)；禁止 Kratos / Kafka / pgvector / PostgreSQL / 打车项目内容 |
| 三 Agent | 开发、测试、验收必须独立会话；验收 Agent 对业务与测试代码**只读**；AI 自述「通过」不作为验收依据 |
| 判断依据 | 原始题面 + 对应版本代码与提交哈希 + 真实执行证据；不得仅凭开发 / 测试 Agent 的完成声明 |
| 三轮验证 | 第 1 轮单测 + 覆盖率 ≥85% + `go test -race`；第 2 轮 Apipost 运行导出；第 3 轮浏览器页面验收；顺序不可颠倒 |
| 环境阻塞 | CGO/gcc、真实 MySQL(InnoDB)、meegle、CI/远端权限缺失属于**环境/权限缺失**，记「待补证」，不判定为代码缺陷，也不写成已通过 |
| 历史证据 | 分阶段提交、独立会话、开发前加载记录等历史事实不可事后补造；说明文档不等于交付物本体 |
| 业务边界 | 金额整数分；一单一商品；数量 1 或 2；单价 10000 分；初始可售 5 件；待支付 10 分钟且用服务端时间；迟到支付不改订单状态 |
| 禁止范围 | 购物车、多商品一单、部分退款、售后退货、签收与售后物流、多商户、真实物流、真实支付渠道、完整财务系统、促销优惠 |
| Git | 全部提交在 `dev/01`；禁止直推 `main`；`feat`/`fix` 前须 `meegle workitem get --work-item-id <编号> --project-key r17te9` 并保留原始输出；核验失败禁止提交 |
| PR 门禁 | 单测、覆盖率、race、gofmt/vet、五组场景、独立验收、提交规范、AI/Skill 记录全部通过才允许 PR |
| 敏感信息 | 密钥、访问令牌、演示口令与用户敏感信息一律脱敏；不索取平台隐藏推理 |

## 输入

- 原始题面（含共同要求）、需求文档 v1.0、原型文档 v1.0、任务规划 v1.1、`AGENTS.md` 与 `.agent/01~06`、`commit-convention.md`。
- 对应版本代码与 `git rev-parse HEAD`、接口清单定稿、运行说明。
- 测试 Agent 全部证据：单元测试、`coverage*.out`、race 原始输出、Apipost 运行导出、缺陷与复测记录、测试报告。
- 开发交付清单、Skill 调用记录、AI 过程记录、PR 与部署记录、视频与群提交凭据。
- 已知环境约束清单（CGO、MySQL、meegle、CI、独立会话是否具备）。

## 执行步骤

1. 锁定版本：记录 `git rev-parse HEAD`、PR 源提交、合并提交、制品与运行版本，识别旧证据混用。
2. 建立 `AC-01~AC-25` + 五组场景 + `M-01~M-30` + `V-01~V-08` 的逐项核查矩阵，在查看结果前固定判定标准。
3. 只读核对业务实现与数据：状态机、金额/数量、10 分钟服务端时间、幂等、并发、权限隔离、审计只追加、异常记录不可消失。
4. 复跑可复现命令（`gofmt`、`go vet`、`go build`、`go test`、覆盖率、可运行入口与健康接口、五组场景脚本），保存命令、原始输出与退出码；不修改学生产物。
5. 核对三轮验证与 PR 门禁证据是否**真实存在且与最终版本对应**；未运行、未访问、未播放的项明确列出。
6. 对每个未通过项分类：代码/产物缺陷、环境/权限缺失、过程证据缺失；分别给出证据、影响、最小整改与复验条件。
7. 输出逐项「通过 / 不通过」结论与证据位置；验收后若修改业务代码，标注需重新运行受影响检查并重新验收。
8. 复核「完成声明边界」：只允许在无门禁证据时写「开发草稿完成 / 可提交测试 Agent 验证」。

## 输出格式

| 编号 | 核查项 | 依据 | 实际证据（路径/行号/命令/退出码） | 结论 | 归属分类 | 缺口与复验条件 |
| --- | --- | --- | --- | --- | --- | --- |

另附：版本对应链表、三类问题汇总表、未运行/未访问/未播放清单、门禁核验清单、证据索引。**不输出「验收通过」除非全部必做门禁有真实证据。**

## 失败处理

- 命令无法执行或缺环境：记录命令、原始报错、环境事实，判「待补证」，不判代码缺陷、不写成通过。
- 证据冲突：并列冲突证据与版本，不自动选择有利或不利一方。
- 发现缺陷：只登记「现象 → 影响 → 最小整改 → 复验条件」，交回开发 Agent；验收 Agent 不修改代码后自行判定通过。
- 无法播放视频 / 无法访问平台：标注未检查内容，不凭目录或字幕断言效果。

## 完成标准

- 每个适用必做项都有「通过 / 不通过」结论、证据位置与版本对应；无「已完成」空泛措辞。
- 环境缺失与代码缺陷严格分离，未把 `-race requires cgo`、无 MySQL 实例、无 meegle 权限写成代码错误或写成通过。
- 未运行、未访问、未播放项全部列出；未伪造任何测试、覆盖率、PR、CI、部署或视频记录。
- 输出结果可供验收 Agent 独立会话直接引用，且明确本 Skill 不替代独立验收会话。
