# 单元测试 + 竞态检测技能（unit-test-race）

## Overview

为 `shop-trade` 题目 01 的 `server/service/` 业务包生成第 1 轮单元测试与竞态检测证据。以 MySQL(InnoDB) 事务 + 行锁口径验证库存扣减、订单状态流转、退款幂等，并把 `go test -race` 与覆盖率 ≥85% 作为强制门禁。

## 用途

- 生成 `server/service/` 下核心业务包的 `_test.go` 单元测试与可重复并发验证。
- 自带 `go test -race` 竞态检测、`gofmt`、`go vet` 与覆盖率原始输出。
- 校验库存守恒、订单状态机、迟到支付异常、重复通知幂等、退款与发货互斥。

## 触发场景

- 用户要求生成 service 层单元测试代码、并发验证或 `go test -race` 原始输出。
- 用户要求校验库存扣减、订单状态流转、退款幂等、重复支付/退款通知、迟到支付。
- 用户要求执行三轮验证中的第 1 轮并输出覆盖率与竞态检测证据。

### 不触发

- 生成 `model.go`、`schema.sql`、业务接口代码、Apipost 用例、页面或部署脚本。
- 执行 Apipost 第 2 轮或浏览器第 3 轮；这两轮由后续独立会话完成。
- 修改生产代码、跨角色改写验收报告，或替开发 Agent 修复缺陷。

## 上层约束（强制）

| 维度 | 固定口径 |
| --- | --- |
| 项目 | `shop-trade`，仅题目 01 电商订单交易闭环；不得混入题目 02～20 业务场景 |
| 架构 | GVA（gin-vue-admin）单体架构，单 Go 服务 + 单 MySQL(InnoDB) 实例 |
| 技术栈 | **Gin + GORM + MySQL(InnoDB)**；禁止使用其他数据库产品、方言或驱动 |
| 数据库 | 业务表统一 `ENGINE=InnoDB`、`utf8mb4`；金额一律整数「分」；审计流水只追加、不可修改、不可删除 |
| 并发 | 优先使用 MySQL InnoDB 事务 + 行锁；更新条件必须命中索引，否则行锁升级为表锁并引发超卖风险；禁止用内存计数器、进程内互斥锁、消息中间件或分布式锁替代行锁 |
| 三 Agent | 开发、测试、验收必须使用相互独立会话；测试与验收须读取原始题面与对应版本代码；不得互相代写交付物；AI 自述「通过」不作为验收依据；学生是唯一跨会话协调与确认人 |
| 权限边界 | 测试 Agent 仅可修改 `dev/01` 下测试相关文件、测试脚本、缺陷记录、测试报告；不得修改生产代码；验收 Agent 对业务代码与测试代码只读 |
| GVA 分层 | 业务逻辑全部在 `server/service/`；`core/`、`global/`、`initialize/`、`middleware/`、`config/`、`utils/` 禁止修改；`api/v1`、`router`、`model/request/response` 仅做声明、绑定、路由；禁止跨层直连 gorm |
| 三轮测试 | 第 1 轮单元测试 + `go test -race`（测试 Agent）；第 2 轮 Apipost 接口自动化（测试 Agent）；第 3 轮浏览器页面验收（验收 Agent）；顺序不可颠倒、不可跳过 |
| 覆盖率 | 自编 Go 生产代码整体语句覆盖率 ≥85%，各核心业务包分别 ≥85%；集成测试不得代替单元测试；自编数据库访问、HTTP 处理代码不得自行排除 |
| race | 20 并发下单、退款与发货并发、重复支付/退款回调等含共享并发访问的逻辑必须提供可重复执行的并发验证并执行 `go test -race`，无数据竞争报告 |
| 格式与静态检查 | `gofmt`、`go vet` 全部通过；保留原始输出 |
| 业务口径 | 一单一商品；数量 1 或 2；单价 10000 分；初始可售 5 件；待支付 10 分钟且采用服务端时间；迟到支付不改订单状态，只生成异常支付待处理记录 |
| 终态 | 已取消、已关闭、已退款、已发货；异常记录不能通过直接改写订单状态消失 |
| 幂等 | 渠道交易号唯一；重复支付通知不重复记款；重复退款通知不重复退款；同一交易号不归属两单 |
| 五组场景 | `TST-S1` 活动正常成交、`TST-S2` 缺货与弃单/20 并发抢单、`TST-S3` 售前退款、`TST-S4` 迟到支付、`TST-S5` 操作竞争 |
| 禁止范围 | 购物车、多商品一单、部分退款、售后退货、签收与售后物流、多商户、真实物流、真实支付渠道、完整财务系统、促销优惠、题外功能 |
| Git | 全部提交在 `dev/01`；禁止直接提交或推送 `main`；提交格式 `[类型] [版本号] [需求/Bug编号] 中文描述`；一次 commit 只含一种类型；测试代码与生产代码分开提交 |
| 编号核验 | `feat`、`fix` 提交前执行 `meegle workitem get --work-item-id <数字编号> --project-key r17te9` 并保留实际输出；失败、编号不存在或查询失败禁止提交 |
| PR 门禁 | 单元测试、覆盖率 ≥85%、`go test -race`、`gofmt`、`go vet`、五组场景、Apipost 第 2 轮、浏览器第 3 轮、Agent 验收、提交规范、AI/Skill 记录全部通过；门禁取 `.agent/` 与 `AGENTS.md` 的更严格并集 |
| 质量证据 | 禁止编造测试结果、覆盖率或部署记录；禁止删除失败测试、弱化断言、跳过关键路径、任意排除自编生产代码；敏感信息一律脱敏 |
| 缺陷闭环 | 缺陷 → 登记 → 开发 Agent 在 `dev/01` 以 `fix` 修复并核验编号 → 测试 Agent 复测 → 重新运行受影响门禁 → 验收 Agent 复核 |
| 优先级 | 原始题面 ＞ 需求文档 ＞ 原型设计文档 ＞ 任务规划文档 ＞ 假设清单 ＞ `AGENTS.md` / `.agent/` 约束 ＞ 本 Skill；本 Skill 不覆盖任何上游文档 |
| 冲突消歧 | 显式读取隐藏目录 `.agent/01`～`06` 与根目录 `AGENTS.md`；技术栈以 `.agent/` 的 MySQL(InnoDB) 约束为准；若历史文档存在旧数据库技术栈表述，记录为待学生确认冲突，不自行改写上游文档 |
| Skill 管理 | Skill 文件本身须在 `dev/01` 以 `docs` 类型单独提交，保留历史版本与变更原因；实际调用须写入 `skill-usage.md`；修改 Skill 须经学生确认（C-08） |

## 输入

- 原始题面、需求文档 v1.0、原型设计文档 v1.0、任务规划文档 v1.1。
- `.agent/01-stack-structure.md` 至 `.agent/06-workflow-devflow.md`、根目录 `AGENTS.md`。
- `server/service/` 对应版本源码、`model.go`、`schema.sql`、接口清单、测试计划、提交哈希与缺陷清单。
- 已配置好的 MySQL(InnoDB) 测试库与可控 HTTP 模拟支付渠道服务。

## 执行步骤

1. 在测试 Agent 独立会话中读取输入文档与隐藏目录 `.agent/`，确认当前分支为 `dev/01`、代码版本与证据对应关系。
2. 识别核心业务包：商品与下单、库存预扣/释放、支付通知幂等、迟到支付、售前退款、发货、权限隔离、运营核查、审计流水。
3. 生成 `_test.go` 单元测试，至少覆盖以下断言：
   - 库存扣减：20 个并发请求争抢 5 件不超卖；已占用 + 可售 = 5；取消/关闭各释放一次；重复关闭不多释放；正常售前退款恢复一次；迟到支付退款不二次恢复。
   - 订单状态流转：8 个状态、4 个终态；待支付 10 分钟服务端时间；关闭后成功通知保持终态；退款审核中/处理中暂停发货；已发货不受理售前退款。
   - 退款幂等：连续 3 次相同支付通知仅记款一次；重复退款通知不重复退款；同一渠道交易号不归属两单；首次渠道退款失败保留待处理，重试成功仅恢复一次库存。
4. 在测试夹具中使用 MySQL(InnoDB) 事务与行锁口径；确认订单行、商品可售数量行的更新条件命中索引；禁止用内存计数器或进程内互斥锁模拟并发安全。
5. 执行第 1 轮验证命令并保留原始输出：

```bash
go test -race -coverprofile=coverage.out ./server/service/...
go tool cover -func=coverage.out
gofmt -l .
go vet ./...
```

6. 生成可读覆盖率报告，逐个核心业务包核对 ≥85%；确认整体 ≥85%；确认无数据竞争报告、无格式/静态检查失败。
7. 若任一断言失败，登记缺陷编号、现象、复现步骤与修正要求；交回开发 Agent 在 `dev/01` 以 `fix` 修复；修复后由测试 Agent 从失败轮次复测并重新运行受影响门禁。
8. 汇总测试报告、覆盖率原始文件、race 原始输出、`gofmt`/`go vet` 原始输出、缺陷与复测记录、证据位置清单。
9. 更新 `skill-usage.md`；测试文件按 `test` 类型提交，Skill 自身变更按 `docs` 类型单独提交；`feat`/`fix` 前完成 meegle 核验。

## 输出格式

```text
server/service/**/*_test.go
coverage.out
coverage-report.md
race-output.txt
gofmt-vet-output.txt
test-report.md
defect-recheck-record.md（如有缺陷）
```

控制台摘要须列出实际命令、退出状态、覆盖率数值、race 结论、格式/静态检查结论与证据路径；不得只写「通过」。

## 失败处理

- 测试失败或竞态检测报告数据竞争：登记缺陷并交回开发 Agent 修复；禁止删除失败 case 或弱化断言。
- 覆盖率不足：补充真实单元测试，禁止排除自编生产代码或用集成测试替代单元测试。
- `gofmt`、`go vet` 失败：登记缺陷并修复后重跑受影响检查。
- 缺少接口清单、模型或测试库配置：停止并列出缺失项，等待学生确认；禁止编造依赖或结果。
- 发现题外功能或其他数据库技术栈：拒绝生成对应测试并记录违规点。
- meegle 核验失败：禁止提交关联 `feat`/`fix`。
- 验收后修改业务代码：重新运行受影响单元测试、race、覆盖率与后续轮次，并由验收 Agent 复核。

## 完成标准

- 全部 `_test.go` 位于测试 Agent 可修改范围，未改动生产代码。
- 库存扣减、订单状态流转、退款幂等、迟到支付、重复通知、并发竞争断言均有实际执行结果。
- `go test -race` 无数据竞争报告；`gofmt`、`go vet` 通过。
- 整体语句覆盖率 ≥85%，各核心业务包分别 ≥85%，原始文件与可读报告齐全。
- 三轮验证顺序记录清晰：本 Skill 仅完成第 1 轮，Apipost 第 2 轮与浏览器第 3 轮未被冒充完成。
- 缺陷、修正要求、复测记录与证据位置可追溯到提交版本。
- 输出中文、证据真实、敏感信息已脱敏；`skill-usage.md` 已登记本次实际调用。
- 本 Skill 产物可作为 PR 门禁证据，不能仅凭 AI 自述判定通过。

## 常见错误

| 错误 | 修正 |
| --- | --- |
| 用内存计数器验证超卖 | 改为 MySQL(InnoDB) 事务 + 行锁与索引命中的真实并发验证 |
| 跳过 `go test -race` | 补跑并保存原始输出，无数据竞争报告才算通过 |
| 删除失败测试或弱化断言 | 恢复断言，登记缺陷并按闭环修复 |
| 用集成测试代替单元测试凑覆盖率 | 补充 service 层单元测试，保留覆盖率原始文件 |
| 排除自编数据库访问/HTTP 处理代码 | 取消排除，纳入覆盖率统计 |
| 替开发 Agent 改生产代码 | 交回开发 Agent 在 `dev/01` 以 `fix` 修复，测试 Agent 只复测 |
| 把 Apipost / 浏览器验收写成已完成 | 保留第 2、3 轮待后续独立会话执行的状态 |
