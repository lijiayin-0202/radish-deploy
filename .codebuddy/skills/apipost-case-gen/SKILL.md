# Apipost 接口用例生成技能（apipost-case-gen）

## Overview

为 `shop-trade` 题目 01 基于已确认的接口清单生成三轮验证中第 2 轮的 Apipost 自动化测试用例。覆盖五组强制演示场景，并包含正常链路、异常链路与 20 并发抢单超卖防护场景。

## 用途

- 把接口清单映射为 Apipost 用例集合、请求参数、前置条件、断言与运行结果导出。
- 覆盖 `TST-S1`～`TST-S5`，并保证正常、异常、并发超卖、重复通知、迟到支付、退款发货并发、越权等分支均有断言。
- 产出可供验收 Agent 引用的第 2 轮证据，不冒充第 1 轮单元测试或第 3 轮浏览器页面验收。

## 触发场景

- 用户要求基于接口清单生成 Apipost 自动化测试用例、接口自动化脚本或运行结果导出。
- 用户要求覆盖五组强制演示场景、正常/异常/并发超卖链路，或核对 `M-01~M-30` 中文失败原因。
- 用户要求执行三轮验证中的第 2 轮并输出接口用例与断言证据。

### 不触发

- 生成 `model.go`、`schema.sql`、service 业务代码、单元测试、页面或部署脚本。
- 执行第 1 轮单元测试 + `go test -race`，或执行第 3 轮浏览器页面验收。
- 在缺少接口清单时编造接口、路径、请求体或响应结构。
- 修改生产代码、跨角色改写单元测试或验收报告。

## 上层约束（强制）

| 维度 | 固定口径 |
| --- | --- |
| 项目 | `shop-trade`，仅题目 01 电商订单交易闭环；不得混入题目 02～20 业务场景 |
| 架构 | GVA（gin-vue-admin）单体架构，单 Go 服务 + 单 MySQL(InnoDB) 实例 |
| 技术栈 | **Gin + GORM + MySQL(InnoDB)**；禁止使用其他数据库产品、方言或驱动 |
| 第三方 | 支付渠道全部为可控 HTTP 模拟服务；不得宣称为真实第三方接入成果；禁止真实支付渠道、真实物流 |
| 数据库 | 业务表统一 `ENGINE=InnoDB`、`utf8mb4`；金额一律整数「分」；审计流水只追加、不可修改、不可删除 |
| 并发 | 优先使用 MySQL InnoDB 事务 + 行锁；更新条件必须命中索引，否则行锁升级为表锁并引发超卖风险；禁止用内存计数器、消息中间件或分布式锁替代行锁 |
| 三 Agent | 开发、测试、验收必须使用相互独立会话；测试与验收须读取原始题面与对应版本代码；不得互相代写交付物；AI 自述「通过」不作为验收依据；学生是唯一跨会话协调与确认人 |
| 权限边界 | 测试 Agent 仅可修改 `dev/01` 下测试相关文件、测试脚本、缺陷记录、测试报告；不得修改生产代码；验收 Agent 对业务代码与测试代码只读；本 Skill 仅生成 Apipost 用例与证据 |
| GVA 分层 | 业务逻辑全部在 `server/service/`；`core/`、`global/`、`initialize/`、`middleware/`、`config/`、`utils/` 禁止修改；`api/v1`、`router`、`model/request/response` 仅做声明、绑定、路由；禁止跨层直连 gorm |
| 三轮测试 | 第 1 轮单元测试 + `go test -race`（测试 Agent）；第 2 轮 Apipost 接口自动化（测试 Agent）；第 3 轮浏览器页面验收（验收 Agent）；顺序不可颠倒、不可跳过；第 1 轮通过后才执行本 Skill，第 3 轮由验收 Agent 后续执行 |
| 覆盖率门禁 | 第 1 轮整体与核心业务包覆盖率均 ≥85%；本 Skill 不降低该门禁，不编造覆盖率 |
| 接口断言 | 全部用例通过；5 组场景端到端链路断言满足；正常回调、重复回调、迟到回调、退款成功、退款失败、验签失败、金额不符、未知订单均可由模拟渠道触发并核查 |
| 业务口径 | 一单一商品；数量 1 或 2；单价 10000 分；初始可售 5 件；待支付 10 分钟且采用服务端时间；迟到支付不改订单状态，只生成异常支付待处理记录 |
| 终态 | 已取消、已关闭、已退款、已发货；异常记录不能通过直接改写订单状态消失 |
| 幂等 | 渠道交易号唯一；重复支付通知不重复记款；重复退款通知不重复退款；同一交易号不归属两单 |
| 五组场景 | `TST-S1` 活动正常成交、`TST-S2` 缺货与弃单/20 并发抢单、`TST-S3` 售前退款、`TST-S4` 迟到支付、`TST-S5` 操作竞争 |
| 失败原因 | 用例断言须引用 `M-01~M-30` 中文原因；无空结果、无写死成功；关联 `AC-01~AC-25`、`V-01~V-08`、`E-01~E-16` |
| 禁止范围 | 购物车、多商品一单、部分退款、售后退货、签收与售后物流、多商户、真实物流、真实支付渠道、完整财务系统、促销优惠、题外功能 |
| Git | 全部提交在 `dev/01`；禁止直接提交或推送 `main`；提交格式 `[类型] [版本号] [需求/Bug编号] 中文描述`；一次 commit 只含一种类型；测试代码与生产代码分开提交 |
| 编号核验 | `feat`、`fix` 提交前执行 `meegle workitem get --work-item-id <数字编号> --project-key r17te9` 并保留实际输出；失败、编号不存在或查询失败禁止提交 |
| PR 门禁 | 单元测试、覆盖率 ≥85%、`go test -race`、`gofmt`、`go vet`、五组场景、Apipost 第 2 轮、浏览器第 3 轮、Agent 验收、提交规范、AI/Skill 记录全部通过；门禁取 `.agent/` 与 `AGENTS.md` 的更严格并集 |
| 质量证据 | 禁止编造接口运行结果、覆盖率或部署记录；禁止删除失败用例、弱化断言、跳过关键路径；密钥、访问令牌、演示口令、签名密钥一律脱敏 |
| 缺陷闭环 | 缺陷 → 登记 → 开发 Agent 在 `dev/01` 以 `fix` 修复并核验编号 → 测试 Agent 复测 → 重新运行受影响门禁 → 验收 Agent 复核 |
| 优先级 | 原始题面 ＞ 需求文档 ＞ 原型设计文档 ＞ 任务规划文档 ＞ 假设清单 ＞ `AGENTS.md` / `.agent/` 约束 ＞ 本 Skill；本 Skill 不覆盖任何上游文档 |
| 冲突消歧 | 显式读取隐藏目录 `.agent/01`～`06` 与根目录 `AGENTS.md`；技术栈以 `.agent/` 的 MySQL(InnoDB) 约束为准；若历史文档存在旧数据库技术栈表述，记录为待学生确认冲突，不自行改写上游文档 |
| Skill 管理 | Skill 文件本身须在 `dev/01` 以 `docs` 类型单独提交，保留历史版本与变更原因；实际调用须写入 `skill-usage.md`；修改 Skill 须经学生确认（C-08） |

## 输入

- 原始题面、需求文档 v1.0、原型设计文档 v1.0、任务规划文档 v1.1。
- `.agent/01-stack-structure.md` 至 `.agent/06-workflow-devflow.md`、根目录 `AGENTS.md`。
- 经学生确认的接口清单：路径、方法、请求参数、响应字段、鉴权方式、角色权限、错误码与 `M-xx` 文案。
- `dev/01` 对应代码版本、提交哈希、第 1 轮单测/race/覆盖率通过记录、可控 HTTP 模拟支付渠道触发入口与演示数据基线。
- Apipost 环境配置、变量命名规则与导出格式要求。

## 执行步骤

1. 在测试 Agent 独立会话中读取输入文档与隐藏目录 `.agent/`，确认分支为 `dev/01`、接口清单已确认、第 1 轮门禁已通过。
2. 校验接口清单完整性：商品与下单、支付通知、退款、发货、异常查询、运营核查、模拟渠道触发、权限校验；缺失则停止并列出缺失项，不编造接口。
3. 建立场景映射表，把每个接口用例关联到 `TST-S1~S5`、`AC-xx`、`V-xx`、`M-xx`、`E-xx` 与预期持久化结果。
4. 生成五组场景用例：
   - `TST-S1` 活动正常成交：运营上架 → 买家下单 2 件 → 支付成功 → 仓库发货 → 买家查运单 → 运营核查；断言 20000 分、已发货、可售 3 件、发货 1 条、异常 0 条。
   - `TST-S2` 缺货与弃单：20 个并发下单争抢 5 件；断言无超卖、已占用 + 可售 = 5、被拒原因、取消/关闭各释放一次、重复关闭不多释放、释放后可再次购买。
   - `TST-S3` 售前退款：申请 → 仓库发货被拒 → 客服同意 → 首次渠道退款失败 → 重试成功；断言暂停发货、失败待处理、仅恢复一次库存、买家可见退款结果。
   - `TST-S4` 迟到支付：订单关闭 → 成功通知到达 → 异常列表 → 客服核实记原因 → 发起退款 → 运营核查；断言订单保持已关闭终态、不重占库存、异常记录可查、退款至多一次、不二次恢复库存。
   - `TST-S5` 操作竞争：退款申请与发货并发、重复支付/退款通知、越权；断言只形成一种合法业务结果、重复通知幂等、同一交易号不归属两单、越权明确拒绝并留痕。
5. 为每组场景补齐正常、异常与并发超卖断言；异常断言覆盖验签失败、金额不符、未知订单、渠道交易号重复、退款失败、已发货申请退款、重复发货、重复关闭、越权。
6. 配置 Apipost 环境变量与前置/后置脚本；从可控 HTTP 模拟支付渠道触发 8 类通知结果；所有断言读取服务返回的持久化结果，不使用写死成功。
7. 执行 Apipost 用例集，导出运行结果；对失败用例登记编号、现象、复现步骤、修正要求与证据位置。
8. 交回开发 Agent 在 `dev/01` 以 `fix` 修复缺陷；测试 Agent 从失败轮次复测并重新运行受影响门禁；验收 Agent 后续执行第 3 轮浏览器页面验收。
9. 汇总用例清单、断言矩阵、运行导出结果、失败与复测记录、对应提交版本；更新 `skill-usage.md`；用例与证据按 `test` 类型提交，Skill 自身变更按 `docs` 类型单独提交。

## 输出格式

```text
apipost-collection.json
apipost-case-list.md
apipost-assertion-matrix.md
apipost-run-export.json
apipost-run-summary.md
defect-recheck-record.md（如有缺陷）
```

控制台摘要须列出场景编号、用例数、通过/失败数、实际运行命令或 Apipost 运行标识、导出文件路径、对应提交版本；不得只写「通过」。

## 失败处理

- 缺少接口清单、鉴权方式、响应字段或模拟渠道触发入口：停止生成，列出缺失项，等待学生确认；禁止编造接口或结果。
- 第 1 轮单元测试、覆盖率或 race 未通过：不得开始第 2 轮；记录阻塞原因。
- 用例失败或断言不满足：登记缺陷，交回开发 Agent 修复；禁止删除失败用例、弱化断言或写死成功。
- 并发超卖断言出现库存不守恒：登记为高优先级缺陷，修复后重新执行并发用例与受影响门禁。
- 发现题外功能、其他数据库技术栈或真实第三方接入成果：拒绝纳入用例并记录违规点。
- 敏感信息出现在请求、响应、截图或导出中：立即脱敏后重新导出，不得提交明文。
- meegle 核验失败：禁止提交关联 `feat`/`fix`。
- 验收后修改业务代码：重新运行受影响接口用例与后续轮次，并由验收 Agent 复核。

## 完成标准

- 接口清单已逐项映射到 `TST-S1~TST-S5`、`AC-xx`、`V-xx`、`M-xx`、`E-xx`。
- 五组强制演示场景均有 Apipost 用例、正常/异常/并发超卖断言与实际运行结果。
- 20 并发抢单不超卖、库存守恒、退款发货并发唯一合法结果、重复通知幂等、迟到支付终态不变、越权拒绝均有证据。
- Apipost 第 2 轮全部通过；运行导出、失败用例与复测记录、版本对应关系齐全。
- 未修改生产代码；未冒充第 1 轮单元测试或第 3 轮浏览器页面验收。
- 输出中文、证据真实、敏感信息已脱敏；`skill-usage.md` 已登记本次实际调用。
- 本 Skill 产物可作为 PR 门禁与验收 Agent 的证据，不能仅凭 AI 自述判定通过。

## 常见错误

| 错误 | 修正 |
| --- | --- |
| 无接口清单却自行编造路径与字段 | 停止并请求学生确认接口清单 |
| 只演示成功主路径 | 补齐 5 组场景、异常分支与并发超卖断言 |
| 用写死成功结果代替服务返回 | 改为读取持久化结果与 `M-xx` 中文原因 |
| 把第 2 轮写成第 3 轮浏览器验收已完成 | 保留第 3 轮由验收 Agent 后续执行的状态 |
| 漏掉重复通知、迟到支付、越权断言 | 按 `TST-S5`、`E-14`、`AC-10`、`AC-16` 补齐 |
| 提交含密钥/口令的导出文件 | 脱敏后重新导出，禁止提交明文 |
| 替开发 Agent 改生产代码 | 登记缺陷并在 `dev/01` 以 `fix` 交回修复 |
