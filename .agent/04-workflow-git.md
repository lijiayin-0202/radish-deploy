# 04 Git 工作流与提交规范

| 项 | 内容 |
| --- | --- |
| 适用项目 | `shop-trade`（题目 01 电商订单交易） |
| 文档定位 | `.agent/04-workflow-git.md`：提交规范、分支、PR、冲突处理 |
| 规范来源 | 根目录 `commit-convention.md`（题集随附来源副本，原文不作改写）；题面共同要求第 8、9 节 |
| 业务范围 | 仅题目 01 电商订单交易，不引入任何其他业务域 |

## 1. 分支规则

| 编号 | 规则 |
| --- | --- |
| B-01 | 通过 GitHub MCP 创建本题独立仓库，保留工具名称、请求与结果、时间、仓库 URL；不得用手工或 CLI 创建记录替代 |
| B-02 | 默认主分支为 `main`；开发分支为 **`dev/01`** |
| B-03 | 业务代码、测试、原型、约束、Skill、配置及后续文档变更**全部在 `dev/01` 提交和推送**；**禁止直接提交或推送 `main`** |
| B-04 | `main` 受保护：禁止直接推送、禁止删除、禁止强推；仅通过 PR 合并且状态检查通过 |
| B-05 | 全程在 `dev/01` 按需求、原型、计划、开发、测试、验收阶段保留真实提交，不得开发结束后一次性补造 |
| B-06 | 合并优先采用保留原始提交的方式，保留开发分支原始提交与 PR 可追溯关系；不得用混合类型的压缩提交掩盖历史 |
| B-07 | 合并后针对 `main` 实际发布提交重新执行质量门禁、构建与部署；开发分支旧版本报告不得当作主分支已验证证据 |

## 2. 提交格式

依据根目录 `commit-convention.md`：

```text
[类型] [版本号] [需求/Bug编号] 描述
```

- 描述使用中文、简洁明了。
- 版本号格式 `v{主版本}.{次版本}.{修订号}`，如 `v2.1.0`。
- 编号为飞书项目真实工作项 ID（需求或缺陷），格式 `#数字`，必须属于相应需求或缺陷。
- 不得因为缺编号把功能变更伪装成 `docs`、`test` 或 `opt`。

## 3. 类型与必填规则

| 类型 | 用途 | 版本号 | 编号 | 本题典型用法 |
| --- | --- | --- | --- | --- |
| `feat` | 新增功能需求 | 必填 | 必填 | 下单、支付回调、退款、发货、页面实现 |
| `fix` | 修复已登记飞书 Bug | 必填 | 必填 | 缺陷清单中登记的修复 |
| `hotfix` | 线上紧急修复 | 必填 | 可选（事后补） | 仅真实线上紧急修复，须保留补录记录 |
| `opt` | 性能、代码质量、重构等优化 | 必填 | 可选 | 重构与优化 |
| `docs` | 文档变更 | 可选 | 可选 | 需求/原型/任务/AGENTS/Skill 文档 |
| `test` | 测试相关 | 可选 | 可选 | 单元测试、并发验证、测试报告 |

本题合规示例（占位符须替换为经核验的真实编号，不得提交含占位符的消息）：

```text
[feat] [v1.0.0] [#<真实需求编号>] 实现订单创建与库存预扣
[fix] [v1.0.1] [#<真实Bug编号>] 修复重复支付通知重复记款
[docs] 更新订单状态说明
[test] 补充迟到支付场景单元测试
[hotfix] [v1.0.2] 修复线上支付回调超时
```

## 4. meegle 工作项编号校验（强制）

- `feat`、`fix` 提交前，必须由 AI 执行并**保留实际输出**（命令、执行时间、完整结果）：

```bash
meegle workitem get --work-item-id <数字编号> --project-key r17te9
```

- **校验失败、编号不存在或查询失败禁止提交**；须提醒开发者确认编号，未完成确认和有效核验前该提交不视为合规。
- 编号必须属于相应需求或缺陷，不得只验证「有这个数字」或关联无关工作项；不得默认改用其他 project-key。
- 不得伪造编号、不得声称查询成功；核验输出须随作业提交。
- 普通缺陷须先登记 Bug，`fix` 才能引用；`hotfix` 仅用于真实线上紧急修复，编号可事后补，不用于跳过日常编号要求。
- `docs`、`test` 可省略版本号与编号；`opt` 版本号必填、编号可选；`hotfix` 版本号必填。

## 5. 一次 commit 一种变更类型

| 编号 | 规则 |
| --- | --- |
| C-01 | 一次 commit 只包含一个类型；混合变更必须拆分为多次 commit |
| C-02 | 业务代码与文档变更分开提交；测试代码与生产代码分开提交；GVA 骨架生成产物与手写 service 分开提交 |
| C-03 | 不得把 `feat` 拆成多个 `docs`/`test` 以规避编号核验 |
| C-04 | 每个提交须能追溯到任务规划文档中的任务编号与对应需求 / Bug 工作项 |

## 6. PR 门禁

| 门禁项 | 判定标准 | 证据 |
| --- | --- | --- |
| 单元测试 | 全部通过 | 测试原始输出 |
| 覆盖率 | 整体 ≥85%，各核心业务包分别 ≥85% | 覆盖率原始文件与可读报告 |
| 并发竞争检测 | `go test -race` 通过、无数据竞争报告 | race 原始输出 |
| 接口自动化 | Apipost 三轮验证第 2 轮全部通过 | Apipost 运行导出 |
| 浏览器页面验收 | 三轮验证第 3 轮全部通过，5 组场景已演示 | 页面结果与脱敏截图 |
| 格式与静态检查 | `gofmt`、`go vet` 通过 | 检查原始输出 |
| Agent 验收 | 独立验收会话逐项通过，有结论与证据位置 | 验收报告 |
| Git 流程 | 全部提交在 `dev/01`、格式合规、编号核验真实、历史可追溯 | 提交与核验记录 |
| AI 与 Skill 记录 | 会话导出、Skill 使用记录、`skill-usage.md` 齐全 | 过程证据 |

**全部通过才允许从 `dev/01` 向 `main` 发起 PR**。PR 须附需求与缺陷编号、变更说明、实际测试结果、覆盖率、验收报告及 AI/Skill 记录位置；状态检查通过后方可合并；质量检查失败不得继续发布。

## 7. 冲突处理（强制在 `dev/01` 解决）

| 编号 | 规则 |
| --- | --- |
| F-01 | **所有冲突只在 `dev/01` 解决，禁止在 `main` 上直接解决或直接推送**；合并后发现问题同样回到 `dev/01` 修正并重新发起 PR |
| F-02 | 解决前先记录：冲突文件、冲突双方提交哈希、解决人、解决方式与时间 |
| F-03 | 禁止强推覆盖他人提交、禁止删除或抹去他人历史；优先采用保留原始提交的合并方式 |
| F-04 | 冲突解决后必须重新执行受影响门禁（单元测试、覆盖率、race、Apipost、浏览器页面验收、Agent 验收），再更新或重新发起 PR |
| F-05 | 禁止以「删除失败测试」「弱化断言」「丢弃他人业务规则」的方式消除冲突 |

| 冲突类型 | 处理责任 | 处理方式 | 复核要求 |
| --- | --- | --- | --- |
| `server/service/` 业务代码冲突 | 开发 Agent | 合并双方改动，逐条核对原题 8 条规则，不得丢弃任一方的状态机、幂等或事务逻辑 | 重新单测 + race + Apipost 相关用例 |
| GVA 生成骨架冲突 | 开发 Agent | 先确认生成范围，必要时重新生成骨架后恢复手写 service 文件；禁止生成器覆盖业务代码 | 核对生成记录与文件清单 |
| 文档 / 原型冲突 | 学生确认后处理 | 以最新需求文档与原型文档为准，`docs` 类型单独提交 | 核对文档版本与任务编号 |
| 单元测试 / 测试脚本冲突 | 测试 Agent | 合并用例，不得删除失败用例或弱化断言 | 重新统计覆盖率与 race 结果 |
| CI / 配置冲突 | 学生确认后处理 | 保留门禁完整性，不得弱化覆盖率与竞争检测门禁 | 重新跑流水线 |
| PR 与 `main` 版本不一致 | 学生 | 在 `dev/01` 更新至最新 `main` 后解决，重新检查最终待合并内容 | 重新执行全部门禁 |

## 8. 合并与版本对应

- 开发分支测试、PR 检查、Agent 验收与合并必须有明确的提交版本对应关系。
- 合并提交哈希与源提交不同，须记录 PR 与源提交关系，并对主分支实际发布提交重新执行流水线门禁。
- 部署制品、上线服务与上线验证必须对应该发布提交。
- 合并后失败修复一律在 `dev/01` 进行，重新发起 PR；回退须记录实际操作与结果，不抹除原始历史。
