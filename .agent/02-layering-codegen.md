# 02 分层与代码生成约束

| 项 | 内容 |
| --- | --- |
| 适用项目 | `shop-trade`（题目 01 电商订单交易） |
| 文档定位 | `.agent/02-layering-codegen.md` |
| 核心约束 | **GVA 脚手架自动生成的底层框架代码禁止修改；业务逻辑全部写在 `server/service/` 层** |
| 并发策略 | MySQL InnoDB 事务 + 行锁优先，不使用 Kafka / 分布式锁 |
| 业务范围 | 仅题目 01 电商订单交易，不引入任何其他业务域 |

## 1. 分层职责

| 层 | 允许做 | 禁止做 |
| --- | --- | --- |
| `api/v1` | 请求绑定、基础参数校验、调用 service、封装响应、展示失败原因 | 写业务规则、直接操作 gorm / DB、直接改库存或订单状态 |
| `service` | **全部业务逻辑**：状态机、库存、幂等、退款、发货、权限、审计、事务边界 | 处理 HTTP 请求对象、拼接页面 |
| `model` / `request` / `response` | 数据结构与请求/响应结构声明 | 写业务流程 |
| `router` | 注册本题路由与中间件引用 | 写业务逻辑 |
| `initialize` / `global` / `config` / `middleware` / `utils` / `core` | 框架能力，仅通过配置使用 | **任何源码修改** |
| `migrate` | 建表、初始化、演示数据 | 写运行时业务规则 |

## 2. 禁止修改清单（GVA 底层框架代码）

| 路径 | 说明 | 例外 |
| --- | --- | --- |
| `server/core/` | 启动入口 | 无 |
| `server/global/` | 全局配置与 DB 句柄 | 无 |
| `server/initialize/` | 框架初始化流程 | 仅通过配置项接入，不改源码 |
| `server/middleware/` | 框架中间件 | 无 |
| `server/config/` | 配置结构定义 | 允许扩展配置值，不改结构源码 |
| `server/utils/` | 框架通用工具 | 无 |
| 框架自带通用 CRUD 能力 | 脚手架生成的基础能力 | 无 |

> 确需扩展框架能力时，须新增独立文件或通过配置项实现，不得改动框架源码；变更须经学生确认并以 `docs` 类型单独提交。

## 3. 代码生成器使用规则

| 编号 | 规则 |
| --- | --- |
| G-01 | 生成器产出的 `api`、`router`、`model`、`request`、`response` 骨架仅作为结构声明，**不得在生成器输出文件内手写业务逻辑** |
| G-02 | 本题业务逻辑写在 `server/service/` 下独立命名文件，避免被再次生成覆盖；重新生成前须确认不会覆盖手写 service |
| G-03 | 禁止反复生成覆盖已含业务的文件；生成记录须保留（时间、模板、目标文件、执行人） |
| G-04 | 生成器不产生业务规则：原题 8 条规则、状态机、幂等、并发裁决、权限隔离均由 service 手写实现 |
| G-05 | **禁止跨层直连 gorm**：`api` 层不得持有或调用 DB，必须经 service；`router` 不得访问数据层 |
| G-06 | 页面只调用后端接口取数，不得内置业务判断或写死成功结果 |

## 4. 业务逻辑落点（service 层）

| 业务能力 | service 落点 | 必须满足 |
| --- | --- | --- |
| 下单与库存预扣 | 商品 / 订单 service | 同一事务内「校验可售 → 预扣 → 创建订单 → 写审计」；20 并发不超卖 |
| 超时关闭与主动取消 | 订单 service | 服务端时间；释放一次；重复关闭不多释放 |
| 支付通知 | 支付 service | 鉴权、订单、金额、渠道交易号、有效期五项校验；幂等记款一次 |
| 迟到支付 | 异常支付 service | 不更新订单状态，仅插入异常支付待处理记录 |
| 售前退款 | 退款 service | 整单全额；审核原因；渠道成功/失败重试；库存恢复一次 |
| 发货 | 发货 service | 仅合法待发货；承运方与运单号登记一次 |
| 核查与权限 | 核查 service | 按订单查询四类记录与汇总（只读）；越权明确拒绝 |
| 审计 | 审计 service | 随状态变更只追加记录 |

## 5. 并发安全：MySQL InnoDB 事务 + 行锁（强制优先）

| 编号 | 规则 |
| --- | --- |
| L-01 | **单订单粒度串行**：所有订单状态变更在同一事务内先锁定订单行再判定状态；退款申请与发货并发只形成一种合法业务结果 |
| L-02 | **库存行锁定**：锁定商品可售数量行后在同一事务内完成校验与预扣；20 并发下单不超卖，已占用 + 可售 = 5 |
| L-03 | **事务边界**：订单状态变更、库存变化、收款/退款记录、发货登记、异常记录、审计流水在同一事务提交；禁止「有订单无占用」「有扣款无订单」 |
| L-04 | **幂等**：渠道交易号唯一约束 + 事务内判重；重复支付通知不重复记款，重复退款通知不重复退款 |
| L-05 | **迟到支付**：命中已关闭订单时不更新订单行状态，仅插入异常支付记录；其退款不产生库存恢复 |
| L-06 | 禁止用内存计数器、进程内互斥锁替代 DB 行锁；禁止用消息队列削峰；禁止在事务外依据旧查询值做二次判定 |
| L-07 | 所有含共享并发访问的逻辑须有可重复执行的并发验证并跑 `go test -race`（见 `05-testing-acceptance.md`） |
| L-08 | **索引命中（MySQL InnoDB）**：L-01~L-07 所述事务均为 MySQL InnoDB 事务；锁定订单行与商品可售数量行的更新条件必须命中索引，否则行锁会升级为表锁，引发超卖风险 |

## 6. 事务与数据一致性红线

- 金额一律整数分，不使用浮点数。
- 库存变化按「预扣 / 取消释放 / 关闭释放 / 正常售前退款恢复」逐笔留痕，同一订单同一原因至多一笔。
- 审计流水只追加、不可修改、不可删除；异常记录不能通过直接修改订单状态消失。
- 角色身份由服务端会话解析，不信任请求参数中的用户编号。
- 业务表建表统一指定 `ENGINE=InnoDB`、字符集 `utf8mb4`。

## 7. 禁止事项

| 编号 | 禁止 |
| --- | --- |
| P-01 | 修改 `core`、`global`、`initialize`、`middleware`、`config`、`utils` 等框架源码 |
| P-02 | 在 `api` 层写业务规则或直接操作 gorm |
| P-03 | 在生成器输出文件内手写业务逻辑、反复生成覆盖手写代码 |
| P-04 | 引入 Kratos、Kafka、pgvector、微服务拆分、分布式锁、真实第三方支付、真实物流 |
| P-05 | 新增购物车、售后退货、一单多商品、部分退款、签收与售后物流 |
| P-06 | 用编造接口、写死成功结果或静态页面代替真实 service 实现 |
